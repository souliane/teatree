# skills — local conventions

See the root [`CLAUDE.md`](../CLAUDE.md) for the code-quality bar. This is the source-of-truth skills tree (`plugins/t3/skills` is a symlink to here). This file adds only what is specific to skill authoring.

- **One skill per directory**, each with a `SKILL.md`. Frontmatter keys: `name`, `description`, `compatibility`, `metadata` (with `version`) — plus two relationship keys:
  - `requires:` — the transitive skill-dependency chain (topologically ordered, cycle-checked). Both hard teatree dependencies AND external methodology skills (e.g. `test-driven-development`, `writing-plans` from obra/superpowers) go here; a required skill with no `SKILL.md` in this repo passes through so the `Skill` tool still loads it. Skill loading is otherwise explicit (slash command / phase / cwd-overlay context) — there is no free-text trigger frontmatter.
  - `companions:` — the SOFT counterpart: a suggested-not-mandatory list of complementary skills, surfaced but never enforced (never folded into the hard `requires` chain). Use it when a skill *suggests* a companion without depending on it.
- **Split a long skill; keep the spine.** A `SKILL.md` carries the rules that change a decision — trigger, verdict, always-gated safety lists — and moves the mechanics behind them into `references/*.md`, largest section first. Each spine entry names its reference by repo-relative path (`skills/<skill>/references/<file>.md`) so a dispatch with no `Skill` tool can `Read` it. Move content, never delete it. (`/t3:rules` § "Split Long Skills With Progressive Disclosure".)
- **Ship evals in the central catalog.** A behaviour-bearing skill's evals live under `evals/scenarios/<skill>.yaml` (one file per skill, same `EvalSpec` schema), each spec carrying an explicit `agent_path: skills/<name>/SKILL.md` that attributes it back to the skill. Scenario bodies never live inside the `skills/` tree (that tree is prose only — enforced by `tests/eval_replay/test_no_inline_skill_evals.py`). A pure-doc / methodology skill instead declares a non-empty `eval_exempt: <reason>` frontmatter key. `t3 evals coverage` reports any skill that is neither covered nor exempt as a gap. See `evals/README.md` § "Where evals live" + § "Per-skill coverage gate".
- **A worked example never names a teatree symbol the tree does not have.** An agent skimming a skill cannot tell an illustration from a work item, so a plausible-but-absent `src/teatree/...` path, `teatree.<...>` name, or bare module-local `<module>.<SYMBOL>` reads as a bug to go fix. Either cite a symbol that genuinely exists, or put the illustration in a stand-in namespace the tree has no claim on (`src/acme/...`, `src/<pkg>/...`) and open the block with a one-line `# EXAMPLE — … Nothing here is a work item.` note. `tests/teatree_quality/test_skill_symbol_refs.py` resolves every teatree-shaped reference in `skills/**/*.md` against the live tree and turns red on the rest; a token that is genuinely not an importable name (an entry-point group, a config-section header) carries `<!-- skill-symbol-ref: <reason> -->` on its own line, or on the line introducing the fenced block it exempts.
- **Reference skills by their qualified canonical name** (`t3:<skill>`): names resolve against their owning namespace and a qualifier is never stripped to force a match, so a bare name that collides across namespaces (`t3:review` vs `other:review`) stays distinct (see `architecture-design/SKILL.md` § "Identity and key normalization").
