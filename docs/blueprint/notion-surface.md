# BLUEPRINT Appendix — Headless Notion documents (`t3 notion`)

Detail behind [BLUEPRINT.md](https://github.com/souliane/teatree/blob/main/BLUEPRINT.md) §3 (`backends/notion`). The invariants it implements: an archived page is not a source, every write is verified by re-reading what it wrote, and an incomplete enumeration is a named refusal rather than a plausible subset.

## Credential, identity and failure taxonomy

The page-status sync above is the narrow read; `teatree.backends.notion` is the full document surface an unattended run needs; agents reach it through `t3 notion` and, for the five writes the MCP surface offers, the approval-gated `notion_*` tools (§ Teatree-own write tools). Auth is a Notion **internal integration** token resolved through the `Credential` machinery (env `NOTION_TOKEN`, then the `pass` entry the `notion_token_pass_key` setting routes on this venue, injected as `pass_path_override`; no default entry), failing loud rather than degrading to an unauthenticated read. Which overlay's routing — and write roots — a call runs as is one answer, `core.overlays.notion_identity.notion_overlay`: `--overlay` (else `T3_OVERLAY_NAME`) folded onto its registered name (`teatree` → `t3-teatree`); unnamed, the only overlay that needs Notion or routes a token, or, when several route the SAME entry, the one declaring Notion required. Two different entries are two identities and refuse at exit 3 rather than pick one, unless an exported `NOTION_TOKEN` is itself the identity, when only the write roots are left to decide — the working directory never picks an identity, because the vendored core's own checkout resolves to the core overlay; `whoami` and `doctor` say whether the token came from `$NOTION_TOKEN` or the overlay's entry, every write prints the integration and overlay it writes as on stderr (and stops, writing nothing, when that identity cannot be read), and a missing token names the overlay tried and the one command that fixes that case. Every write verb that takes a body takes it as a file or inline (`--body-file` / `--body-text`; `replace` takes `--old-file` / `--old-text` and `--new-file` / `--new-text`, exactly one of each pair, inline text verbatim), because `t3` runs in a container that does not see host paths; `replace` prints ONE JSON document on stdout, a dry run included, with the human diff on stderr, and `httpx` request lines are off the default log handlers so they never merge into it. The integration must additionally be **shared onto each page/database** — a Notion-side grant no code can perform — and the failure taxonomy (`backends/notion/errors.py`) keeps that condition distinguishable: token missing (3), token rejected (4), capability not granted (5), bot cannot see the id (6), not a Notion object (7), rate-limited (8), write-reported-but-not-landed (9), ambiguous section (10), unrepresentable Markdown (11), property not on the page (12), property unwritable from plain text (13), page not live (14), positioned-append heading absent (15), block not copyable (16), write refused by the write guard (17), enumeration incomplete (18), replace anchor not exactly one editable span (19), block changed since it was read (20), reply discussion not under the page (21), write sent but its outcome unknown (22), MCP write without a recorded approval (23), each its own exit code. A 404 is separated from "bad token" by probing `/users/me`, so exit 6 names the bot (name and bot id) and lists the three causes the API cannot tell apart — not shared with the integration, the id no longer exists, another workspace — with the checks that separate them. `t3 notion setup` is how the token gets there without reading any documentation: it opens the integrations page (`webbrowser.open`, never a Claude-specific browser tool the headless factory does not have), prints the capability checklist Notion grants none of by default, takes the secret on a hidden prompt (no `--token`, so it never reaches argv), writes it to the overlay's own `pass` entry with a timestamped backup of any prior value, verifies it by resolving it BACK through `build_notion_client` — the readers' own path, which is what catches an exported `NOTION_TOKEN` shadowing the entry just written — and reports one line per `--page` and per page an in-flight ticket tracks through the same `page_verdict` triage `t3 notion doctor` exits on. `t3 doctor check` gates the same credential, and `t3 setup` reports it headless, through one probe (`cli/doctor/checks_notion.py`) for every overlay that needs Notion (`required_third_party_services`) or routes a `notion_token_pass_key`, distinguishing unconfigured / absent / rejected / **shared onto nothing** / **tracked page ungranted** — the fourth read via `POST /v1/search`, whose empty result is the only precise signal that a valid token was never granted anything, the fifth a read of every `extra['notion_url']` page an in-flight ticket tracks — because each has a different fix, and silent where Notion is unrouted. A credential's entry name is a per-venue setting (`teatree.config.credential_pass_key`: overlay-scoped `<credential>_pass_key` row, then global, then the overlay's declared `*_PASS_KEY`), so a container reads its OWN `pass` store through the entry its DB routes; the deploy exports `NOTION_TOKEN` only from an explicitly named `NOTION_TOKEN_PASS_PATH`, because an exported value would shadow that routing. It is deliberately never written into `deploy/teatree.env`, which the deploy workflow regenerates wholesale and keeps secret-free. <!-- skill-symbol-ref: teatree.env is gitignored — the deploy workflow writes it on the box, so it is absent from the tree by design -->

## Liveness, writes and discussions

**An archived page is not a source, so the read refuses (`backends/notion/liveness.py`).** An archived Notion page renders as COMPLETELY current — full acceptance criteria, a `Status` still reading "In Progress", live comment threads — so an agent handed one builds against a superseded spec, and an acceptance criterion only the dead page states produces the WRONG work rather than merely wasted work. `PageLivenessProbe` is the predicate every page-scoped command goes through (`cli/notion_support.live_page`, the single chokepoint): `archived`/`in_trash` on the page object is the only signal that CONCLUDES death and is decisive; membership of the page's own parent database is the corroboration, honest about not being an independent detector (the probe queries the parent the page itself declares) and earning its place by turning an unverifiable read into an explicit UNKNOWN and by supplying the SUCCESSOR — the live row sharing the page's title, named in the refusal, or plainly reported unresolvable rather than guessed. Membership is asked the way Notion can answer it: its title filter sees text runs only, so a title carrying a mention (a date, a person) is matched with `contains` on its longest text run, and a row the title query still misses is looked for by page id in a scan capped at 1,000 rows — an `absent_from_parent_database` verdict then says both queries ran and returned what, and only `parent_database_unreadable` (Notion's 404 after the token authenticated) tells the reader to share the database — any other query failure (throttling, a server error, a query the pinned API version refuses) is `parent_database_unverified` and names the real error. Death is a disjunction (any signal suffices) and life a conjunction (every applicable signal evaluated AND agreeing), so a parent database this integration cannot query fails CLOSED at exit 14 rather than reading as fine. `t3 notion doctor` reports the liveness as its own third stage — `OK`/`DEAD`/`UNKNOWN`, never a bare OK it did not establish. The one escape is a READ escape and its OWN command rather than a flag on `fetch`, so it cannot be reached by appending something to the read you were already typing: `t3 notion audit-fetch <page> --reason '<why>'` takes written prose (blank does not unblock), announces itself on stderr, and stamps the emitted Markdown, so an audited body cannot travel as current; there is no audited WRITE. Beyond the CLI, `core.sync` skips a non-live page rather than recording its status onto a live ticket and refuses the write-back, and the `notion_page_status` MCP tool refuses instead of answering — both through the boolean `NotionPageClient.page_is_live` seam, so core honours the rule without importing across the core → backends inversion. Content already held from an earlier read is covered as prose (`skills/ticket/SKILL.md` § "An Archived Page Is Not a Source"), pinned by `evals/scenarios/ticket.yaml::archived_notion_page_is_not_a_source`. `backends/notion/sections.py` is the idempotency primitive the PRD/BDD skills own a named H2 section with: **block-scoped only** — the new body is appended under the matched heading, only that section's enumerated blocks are archived, and a legacy heading is patched in place so its id and its discussions survive. There is deliberately no whole-page replace anywhere on the surface, because re-creating every block destroys the block-level comments attached to them. `t3 notion append --after-heading` reuses that same locator to POSITION a write inside the page — the anchor is the section's last body sibling, or the heading block itself for a toggle heading that owns its body as children — and, unlike `section replace`, it never creates the section it cannot find: an absent heading exits 15 rather than falling back to the end, the one position the caller explicitly did not ask for. `backends/notion/blocks.copyable_blocks` is the primitive for the other direction — copying a section rather than rewriting one: it turns a FETCHED tree back into the postable JSON `append --blocks-file` already takes, dropping the server-owned fields a POST rejects and resolving `has_children` into an inline `children` list, because a fetched `table` carries no rows of its own and re-posting one as fetched yields an empty table or a 400. Copying through Markdown instead is lossy by construction — a callout becomes a quote, a toggle's children flatten to siblings — so fidelity would depend on what the page's author happened to type. A block a POST cannot carry (a child page or database, a synced block, `unsupported`, or a Notion-hosted `file`-variant asset whose signed URL expires) is REFUSED naming the type and the block at exit 16, never silently dropped: a section quietly missing content is worse than a run that said what it could not copy. `t3 notion create <parent> --title` (`backends/notion/pages.py`) makes a child page under a page or database the integration already reaches — Notion's API gives an internal integration no workspace-level create, so a parent the bot cannot see exits 6 with the same causes and checks, plus the integration to share it with — through the same `_write` chokepoint, at most once per title under the parent (`exists` when a same-title page already carries the whole body; a shorter one — an earlier create that stopped part-way — exits 9 naming the missing count and the remedy, nothing written), and verified by re-reading its title and body the way `append` is. `t3 notion replace <page> --old-file --new-file [--dry-run]` (`backends/notion/replace.py`) is the anchored edit: the API has no server-side text replace, so it walks the page's text slots (each block's `rich_text`, each table cell), requires the old text exactly once, edits it inside one run or adjacent runs sharing one formatting (anything else exits 19 rather than flatten formatting), re-reads the whole block just before the PATCH and refuses at exit 20 if any of its text changed since the walk — every cell of a table row, since the PATCH carries them all, and it is built from that re-read (a human edit is never overwritten) — PATCHes only that block, re-walks the page to prove the expected state, refuses a no-op, reports a match lying inside an occurrence of the new text as `already applied` and writes nothing (a retry of a replace whose new text contains the old), compares text AND formatting on read-back, and records one `OutboundClaim` `notion_edit` row per PATCH sent carrying hashes and lengths, never the text — verified when the read-back confirmed it, drift (`not landed`, exit 9) when it did not, and drift (`unverified`, exit 22) when the PATCH may have landed — a 5xx, or a transport failure once the connection opened — or the read-back after it failed; a PATCH Notion refused (429, 4xx), one whose connection never opened, and a write-time guard refusal keep their own exit codes and leave no row; `--dry-run` passes the same write-guard check and prints the slot diff. The guard's refusals name the rule: `notion_write_denied_roots` are pages shared with customers, which the integration never writes. Two further primitives cover what a block tree cannot express, both under the same verify-by-re-read rule: `backends/notion/comments.py` posts a page comment **at most once per marker** (the dedup is the default, keyed on the caller's marker — found anywhere in a comment — or else the whole body, compared normalised and never as a substring, and, for a reply, only within its own discussion; it reports `duplicate` at exit 0 rather than double-posting — the callers are dedup-driven skills, so a forgotten flag must under-post; `allow_duplicate` is the deliberate second copy, and the check sees only Notion's unresolved discussions), and `backends/notion/properties.py` reads any page property as plain text and writes one **shaped by its own live type**, so a caller names a value and never a Notion type. Every write re-fetches and refuses to report success unless what it asked for is what the page now carries. **A page's discussions are not what the page anchor returns (`backends/notion/discussions.py`).** `GET /v1/comments?block_id=<page id>` answers with the threads whose parent is the PAGE, and an inline comment's parent is the BLOCK it is anchored to — measured on one specification page, 1 comment against 13 across 12 discussions — so a page-scoped read hands back a plausible subset and says nothing about it, which is how a requirement gets written against a comment nobody could see. `DiscussionEnumerator` walks the block tree (toggles, tables, child pages, and embedded-database rows through their data sources), reads the comments anchored at each object, follows `has_more`/`next_cursor` on every listing, and keys each `AnchoredComment` to its discussion id, anchor block, author and timestamp so a caller can cite and re-resolve it. Completeness is part of the result rather than the caller's problem: every object the walk could not read becomes a named `CoverageGap`, and a result carrying one exits 18 and renders under an explicit refusal instead of passing as the whole set — a database granting the integration no data source is such a gap, never a silent exclusion. `--verify` enumerates twice and reports any thread one read served and the next omitted, keeping BOTH in the output because dropping the one that vanished reproduces the disappearance the cross-check exists to detect. Each thread is printed with its anchor block's id and text, the coverage line always states what was scanned (`page-level + N block(s) scanned`) and names every object NOT scanned, the count is of objects whose comments were actually read (the page itself is named when its own read failed), and the walk stops at 1,000 objects — an embedded database is queried only up to the remaining budget — with an `object_capped` gap rather than running unbounded. `t3 notion comment on <page> --quote` opens a discussion on the one block holding the quote (the API anchors a new discussion on a whole block, never a selected range) and `t3 notion comment reply <page> --discussion` replies inside a discussion the enumeration found on that page, both marker-deduplicated and verified by re-reading the anchor's comments. And a COMPLETE result is still not an exhaustive one, so `UNPROVABLE_BY_THIS_API` is stated on every result: resolved threads, reaction threads and suggested edits are invisible to the public API, and it publishes no page-level total to reconcile against.
