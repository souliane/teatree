# BLUEPRINT Appendix — One agent per checkout (#3952, #5238)

Detail behind [BLUEPRINT.md](https://github.com/souliane/teatree/blob/main/BLUEPRINT.md) §4 ("One agent per checkout"). The rule it implements: one ticket's checkout is driven by at most one agent at a time, and a run that ends leaves the checkout in a state the next writer can trust.

## Why the claim lives on the `Worktree` row

- The [#3903](https://github.com/souliane/teatree/issues/3903) dedupe stops two `Task` rows for one ticket+phase; it cannot see two agents that ALREADY hold checkouts. Under the autonomous posture the loop mints its own work while operator-dispatched lanes are live and both resolve one ticket to one worktree path — observed on a single branch: a factory agent committing the other's uncommitted edits under its own commit, a `git add -A` staging the other's in-progress files, an unpushed local merge left behind mid-verification.
- The contended resource is the worktree, so the claim lives on the `Worktree` row: `core/worktree/occupancy.py` carries the same #786 compare-and-swap as `task_claim` (ONE conditional `UPDATE … WHERE <grantable>` whose row count IS the decision — a read-then-write races on SQLite, where `select_for_update` is a silent no-op), keyed on the fully-qualified `(holder, holder_session)` pair so a same-holder re-acquire refreshes while a rival is refused.
- **Advisory toward a rival.** The gate refuses a SECOND requester and never evicts the first: a refusal deletes, reaps or kills nothing, and a lapsed lease grants the next requester without touching the previous holder's process, files or branch. Process signals come from a run's own checkout exit or an explicit owner stop.

## Who holds it, and for how long

- A factory task holds its ticket's dispatch-checkout `Worktree` occupancy as `task:<pk>` before opening its harness, in every phase, on the worker and on interactive `claim-next` alike. `run_headless` holds the claim for the whole run (renewed by the existing task-lease heartbeat); a refused dispatch parks (§ "The writer fence"). A checkout the run creates is held from the first heartbeat that sees it and released and attested by the same exit. Interactive claims take the same extended lease as their task claims.
- `workspace ticket` refuses to hand back an occupied checkout unless `--take-over`; `t3 <overlay> worktree occupancy` / `claim-occupancy` / `release-occupancy` is the surface a hand-driven lane claims through, and `doctor check` reports every live claim.
- A fixed 30-minute lease (`_OCCUPANCY_LEASE_SECONDS`, 30 renewals of the 60s run heartbeat) bounds a claim whose holder died without releasing.

## Release

- `Task.complete()`/`Task.fail()` normally release the claim in the SAME transaction as the terminal status write ([#4867](https://github.com/souliane/teatree/issues/4867)); a holder still driving its run defers release until the exit checks process evidence and attests the checkout, while a confirmed-dead third-party holder releases despite a stale driving marker.
- A `fail()` is either a SELF-report (`by_holder=True`: the claim holder's own process terminalizing its own run, which releases unconditionally) or a THIRD-PARTY fail (`by_holder=False`: an operator `tasks cancel`, `ticket.rework()`, the MCP `task_fail` tool — any client may name any task mid-run), which releases ONLY once `claim_liveness.holder_confirmed_dead` positively proves the recorded owner's process is gone — otherwise the claim is left intact so a still-live holder is never evicted out from under itself ([#4872](https://github.com/souliane/teatree/issues/4872)). The same liveness check gates `worktree_occupancy.terminal_task_pk`'s status-only self-heal, so a withheld third-party claim is not released on the very next dispatch either.
- The kept claim fields do not let the holder land over the cancel: `task_claim._generation_holds` also requires the live row CLAIMED when the caller's instance is a CLAIMED holder, while a fresh-reading operator or sweep keeps the generation-only match, so `tasks complete --note` still completes the FAILED row.
- The transient-requeue sweep skips a FAILED row whose kept claim's Task lease is unexpired (`TaskQuerySet.without_kept_claims`), so neither a reopen nor a retire frees a live holder's checkout; a dispatch refused by such a holder parks (`terminal_holder_task_pk`, status only), bounded by the holder's heartbeat abort or the lease lapse rather than escalated.

## The writer fence

- A writing task also needs, for every checkout of its ticket, exactly one `Worktree` row for the path across all tickets, a host-covering process table with no live process in the checkout, and a checkout state matching `Worktree.extra.attested_state`; first sight attests only a pristine checkout, counted against the ticket's target branch.
- A refusal — an occupied checkout or a failed fence — parks the task under its own `checkout_parked:` reason naming the cause, without spending its repair budget, until the holder's lease expires or 30 minutes pass, and sends one owner notice per episode. A missing attested state is named explicitly with the `worktree attest` action; a changed checkout is never silently accepted.
- An occupancy refusal records the fully qualified holder and session in the parked attempt's `result.occupied_by`, including when the attempt row is coalesced. Releasing that holder wakes only the ticket's pending tasks whose newest attempt names that pair and whose retry time is still in the future; a refusal for another reason keeps its retry time. A post-park holder check closes the release-before-park race without clearing a newer admission stamp. A park that frees a seat and a release that re-arms a task schedule the admission walk after commit; the walk skips tickets whose checkout is still held and sees them again after release or lease lapse.

## Exit attestation and custody re-attestation

- The run's own exit attests in the transaction that releases occupancy. It finishes its own checkout processes and reads the checkout state before that transaction opens (`task_claim.atomic_after_checkout_exit`), so the wait never holds the control DB's write lock. The claim is checked before the wait and under the lock; if it moves during the wait, the cached settle is discarded and release settles without attesting. This covers a completion or failure write, an in-session `/loop` `record-attempt`, a park after it drove (a checkpoint, a usage window, a route failure), and an admitted headless run whose harness raises before its task is terminal. A refused or reaped run releases without attesting; so does an exit whose process table cannot rule out live processes. A process killed before its exit is handled by the next writer's custody proof.
- At the next writer's fence, an interrupted run may instead be re-attested when the custody record proves one writing task held the dispatch checkout continuously until release or lease lapse with no intervening holder, a readable host-covering process table shows no live process there, two state reads agree, and every ticket checkout is on its recorded branch or the forge-reported head branch of an open pull request owned by the ticket. An unreadable forge answer refuses. Two checkouts of the same repo on one ticket may accept each other's pull request head branch because the custody conditions still apply. Unreadable same-user processes still refuse, except a host-root PID namespace process may be set aside when every prior tenure records that its writer ran in a nested PID namespace. Headless runs record that namespace; legacy and other namespace-less tenures stay strict. Every admitted headless exit reaches checkout settlement; when these gaps block direct attestation, the next writer's fence can re-attest, including a claim in the same worker session. The worktree records the holder chain, process source, set-aside processes, branches, qualifying pull requests and digests in `auto_attestation` without paging the owner. Edits from those uninspected host processes during the proof window become trusted state; a process launched through the worker's Docker socket into the host PID namespace can also be set aside. Missing proof leaves the task parked.
- On completion, ordinary failure, lease-expiry reap, or an attested park, checkout settlement checks for the run's descendants and marked children in the checkout over two 60-second beats. It sends SIGTERM to survivors, waits one beat, sends SIGKILL to survivors, then checks over two more beats. Each signal uses a pidfd and rechecks the process's PID and start time. The shared Codex App Server is excluded; unmarked processes outside the run's descendants and foreign processes are never stop targets. Any remaining process keeps the checkout occupied. An agent-issued cancel skips these exit signals.
- A heartbeat renewal preserves the existing tenure's namespace; if it reclaims a free row, the new tenure has no namespace and later recovery remains strict.
- When a writing run's exit cannot release because a process still holds its checkout, it records the holder, session, exit digest and deferral cause in `deferred_exit`. The next writer's fence attests that exit only if its custody tenure immediately follows the deferring tenure, the deferring task was not cancelled, the checkout state still has that digest, and a usable host process table shows no process holding it. The audit retains the deferred record and process-reading gaps in `auto_attestation`; a process still holding the checkout leaves the task parked. This proof does not relax the interrupted-run proof above when no exit record exists.
- A whole-row `Worktree.save()` keeps the live claim columns and the `attested_state`/`checkout_custody`/`auto_attestation`/`deferred_exit` keys, so a stale row cannot erase a holder from the chain; only the occupancy CAS and `merge_extra` write them.
- A record whose task does not hold its checkout is a hand record: it never attests and mints no next phase. The owner may run `worktree attest <path>` directly after inspection or accept an attestable refusal through an authenticated Slack card. The card names the waiting step and what it will do, links the ticket and any open pull request in the checkout's repo that the step may hold up while open (or says none for that folder was open when asked), gives the commit and uncommitted-file counts and whether nothing was found running, and says what Accept and Decline each do; design-review and wrap-up cards link an open pull request without claiming it waits on those steps. A re-ask replaces a pending card for the same task when displayed evidence changes and retires every task's card for an older checkout state; different parked tasks keep their own cards. A retired card's posted buttons are closed. Accepting one retires the other cards for that checkout, rechecks the live state, records the answer, and resumes tasks parked for that checkout except a task whose latest answer for that state was Decline; the writer fence ignores the recorded attestation for such a task, so only a changed checkout, a factory proof, or a new card can let it run. If process evidence is unavailable, an explicit owner attestation admits one dispatch after two matching state reads and is consumed by that dispatch; another dispatch requires renewed owner attestation.
- The stuck-ticket sweep skips a ticket whose newest task in the implied phase was cancelled and mints no coding over a merge-safe review newer than the latest plan; a manual hand record re-dispatches only after the idle threshold, while `/loop` records schedule the next phase immediately. Shipping has the same in-flight task dedupe as coding.

## Cancel keeps the checkout reserved

- A run that lost its lease keeps interrupting every heartbeat until the harness drive returns. Completion and ordinary failure writes, lease-expiry reaps, and attested parks use the exit settlement above. A cancelled runner waits up to two 60-second beats for its own checkout processes; an agent-issued cancel records surviving descendant writers for an owner stop card and signals nothing.
- A surviving process keeps `task:<pk>` occupied until its lease lapses, keeps the terminal row's owner pid so the self-heal leaves the hold, leaves the previous attestation intact and pages the owner once.
- A cancellation issued directly from an owner terminal may signal only the runner's descendants that still have a writable checkout file descriptor after a pidfd identity re-check. An owner answer to an agent-cancel stop card may signal only the recorded descendant writers after a fresh namespace, start-time, file descriptor, and pidfd re-check, and tells the owner when a namespace mismatch stopped nothing. These cancellation stops send SIGTERM. The shared Codex App Server and a marked orphan without runner descent are never cancellation stop targets.
