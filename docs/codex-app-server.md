# Codex App Server harness

Teatree can run a headless agent through the FOSS `codex_app_server` harness. It
starts `codex app-server --listen stdio://`, uses a managed ChatGPT login, and
keeps Codex's thread id as the Teatree agent session id so a parked task can
resume the same server-side thread.

This is a built-in Teatree harness, not a downstream-only overlay and not a Python
Codex SDK. The runtime image pins `@openai/codex@0.155.1`; the harness request
contract is tested against the protocol schema generated by that exact CLI.

## One-time authentication bootstrap

Authenticate on an attended machine, then import the complete credential cache:

```console
codex login --device-auth
t3 codex auth import --from ~/.codex/auth.json
```

When `t3` runs in a container that deliberately cannot see the host's
`~/.codex`, forward the file over standard input instead:

```console
t3 codex auth import --from - < ~/.codex/auth.json
```

The importer reads at most 1 MiB from either source and rejects empty input.

The importer validates the JSON and stores the **entire `auth.json`**, encoded as
exactly one base64 line, at `teatree/codex/auth-json-b64` in the existing `pass`
store. The entry is not an OAuth token. Neither the JSON nor its encoded value is
put in command arguments, logs, or command output.

Configure an agent route with `agent_harness = "codex_app_server"` and leave
`agent_harness_provider` unset. Codex owns the managed ChatGPT authentication;
this route is neither an Anthropic provider nor a metered API-key provider.
With this direct harness setting, Teatree omits `model` and lets Codex select its
own default. An ordered per-skill route can instead pin an explicit Codex model.

Teatree's shipped verification guardrail still pins `testing`, `reviewing`, and
`requesting_review` to `claude_sdk`. Setting the direct default harness to Codex
does not silently remove that checker separation. An operator who deliberately
wants Codex for a verification phase must explicitly override that phase's
`agent_phase_harness`; an ordered per-skill route remains explicit about both its
harness and model.

## Runtime lifecycle and concurrency

The harness ignores an ambient `CODEX_HOME`. It uses the stable private directory
named by `T3_CODEX_HOME`, or Teatree's data directory under `codex-home` by
default. The child receives a minimal allowlisted process environment and its
`HOME` and `CODEX_HOME` both point at that private directory. Direct Claude,
provider, forge, and TeaTree secret values are not inherited. Controlled
factory-owned runtime paths are retained only for TeaTree's config/control DB
and repo. Git receives explicit author/committer identity with a private global
config, no system config, and every inherited credential helper reset; pass/GPG,
XDG, forge CLI, and Git credential-store
paths are withheld. Credential-bearing lifecycle skills must route to a harness
that owns those credentials rather than exposing a store to Codex. Before Codex starts,
Teatree:

1. takes an exclusive file lease shared with the auth importer;
2. reads and validates the pass entry;
3. atomically materializes `auth.json`; and
4. enforces mode `0700` on the directory and `0600` on the cache and lock files.

One worker-owned App Server can host multiple simultaneous Codex threads with
different per-task MCP settings. Their cache persists are serialized after each
task; the process exits five seconds after its last thread, persists once more,
and releases the file lease. An unchanged cache causes no pass write. A new task
starts a new process and revalidates/hydrates the pass entry; a task arriving
during the idle grace reuses the existing process.

This process-start lease is the boot preflight too: Teatree validates and
hydrates before each new Codex process, including the first run after a worker
recreation. It does not copy the credential during container entrypoint startup,
where the cache would sit outside the lease and a Claude-only deployment would
require an unused Codex credential. A missing or invalid Codex credential
becomes a typed authentication fallback when a Codex route is attempted.

One credential cache must have only one active writer. Processes sharing the
same `T3_CODEX_HOME` serialize on the file lease. Separate pods do not share that
lease: keep this authenticated runner at one replica, or acquire a Kubernetes
Lease/shared lock before enabling concurrent Codex runs against the same pass
entry. A hard kill cannot run graceful persistence; the next worker hydrates the
last verified cache from pass.

## Policy translation

- `cwd` and `add_dirs` become Codex runtime workspace roots. Workspace-write
  mode makes those same roots writable.
- Claude's `bypassPermissions` means unattended approval here, not unrestricted
  host access: Codex receives `approvalPolicy = "never"` with workspace-write.
- Read-only policy is preserved. Tool rules Codex cannot faithfully enforce are
  rejected by the phase-aware availability probe before the process starts, so
  an ordered route selects its next harness instead of failing the task. A phase
  that denies delegation sets Codex's `features.multi_agent = false`; a phase
  that denies the shell or all file reads is not Codex-compatible with the
  pinned CLI because it has no equivalent per-tool deny control.
- Inline stdio MCP servers are translated and supported. Remote/non-inline MCP
  configurations are rejected.
- Server-side resume is supported. Claude hooks and native structured output are
  not declared as capabilities.

Authentication, quota, access, transport, and provider 5xx failures are mapped
to Teatree's typed route-fallback errors. An explicit quota/access failure before
an external-effect item may advance to the next configured route. Once Codex has
started a command, file change, or MCP call, Teatree stores the Codex thread id
and parks instead of replaying the turn; the next Codex run resumes that thread.
A stream disconnect after `turn/start` is treated as potentially side-effecting
even if no item arrived, because the client cannot prove what the server did.
Protocol, schema, unsupported-policy, and programmer failures remain hard
harness errors, so a broken adapter cannot silently replay work.

## Rotation, recovery, and revocation

- **Rotate:** authenticate locally again, rerun `t3 codex auth import --from
  ~/.codex/auth.json` (or pipe it with `--from -` when `t3` is containerized).
  The importer waits for active Codex tasks and the five-second idle grace to
  release the lease; the next process hydrates the new entry. The guarded write
  retains the existing pass backup behavior.
- **Recover:** if bootstrap reports missing, invalid-base64, or malformed JSON,
  do not hand-edit the encoded entry. Re-import a known-good complete
  `auth.json`. If App Server reports the account is not managed ChatGPT auth,
  repeat `codex login --device-auth` before importing.
- **Revoke future bootstrap:** revoke the Codex/ChatGPT session and delete the
  `teatree/codex/auth-json-b64` pass entry.
- **Revoke immediately:** also stop the worker and remove the private
  `$T3_CODEX_HOME/auth.json`. Deleting pass alone does not erase a cache already
  materialized in a running worker.

The harness fails before Codex starts when pass cannot be read or validated, and
its remediation always names the pass entry and bootstrap command without
including credential contents.
